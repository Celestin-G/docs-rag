# docs-rag

> 🚧 **Status: proof of concept.** Runs fully locally on your machine — no server deployed yet, no production LLM API connected yet. Response time (30–60s) reflects the local model, not the final product: a hosted LLM API will replace it before any customer-facing launch.

A local RAG (Retrieval-Augmented Generation) engine for the [Formance](https://formance.com) documentation. Ask questions about the platform in natural language — answers are generated by a local LLM using only the official docs as context. No external API keys, no data leaving your machine.

---

## How it works

```
Question → translate EN → embed → hybrid search (vector + BM25) → diversity filter → top chunks → qwen2.5:32b → streamed answer
```

1. **Ingest** — the Formance docs repo is walked, `.md`/`.mdx` files are parsed, MDX/JSX noise is stripped, and the text is split into ~500-token chunks by heading hierarchy (H2 → H3). Each chunk is prefixed with a **full breadcrumb** (`Page Title > H2 > H3`) so the embedding model captures the page context.
2. **Embed** — each chunk is embedded via Ollama (`nomic-embed-text`, 768 dims) using the model's `search_document:` task prefix, and stored in PostgreSQL alongside a `tsvector` column (for full-text search) with a pgvector HNSW index and a GIN index.
3. **Translate** — at query time the question is translated to English (the language of the docs) before embedding, so French or other-language questions match correctly. The query is embedded with the `search_query:` prefix.
4. **Hybrid search** — retrieval combines **vector similarity** (70%) and **BM25 keyword matching** (30%) in a single SQL query. This means exact technical terms (`ErrMetadataOverride`, `fctl ledger send`, `unbounded`) are found reliably even when semantic similarity alone would miss them.
5. **Diversity filter** — the candidate pool (top-k×2) is deduplicated so no single source file contributes more than 2 chunks to the final context.
6. **Generate** — the retrieved chunks are injected into the system prompt of `qwen2.5:32b` via Ollama (temperature 0.2 for factual answers). The model answers strictly from the docs for technical facts, and may synthesise step-by-step guidance from documented concepts. Active filters (version, deployment, license) are also injected so the LLM knows what scope it is operating in. In Community mode, the list of Enterprise-only features is **derived live from the badges in the database** (cached 5 min), so the guard stays in sync with the docs; the model must flag EE features as such, and may offer a clearly-labeled Community alternative when one exists.
7. **Stream** — the answer is streamed token by token to the web UI via SSE. Each answer gets 👍/👎 feedback buttons, stored for quality monitoring.

## Setup

### 1. Clone this repo

```bash
git clone https://github.com/celestingeniaut/docs-rag
cd docs-rag
```

### 2. Clone the Formance docs

```bash
git clone https://github.com/formancehq/docs ~/formance-docs
```

You can put it anywhere — you will point `DOCS_PATH` at it.

### 3. Start PostgreSQL

```bash
docker compose up -d
```

This starts a `pgvector/pgvector:pg17` container on port 5432 with credentials `rag / rag / ragdb`.

### 4. Pull the Ollama models

```bash
# Embedding model (fast, ~270 MB)
ollama pull nomic-embed-text

# Generation + translation model (slow to pull, ~20 GB — grab a coffee)
ollama pull qwen2.5:32b
```

Make sure Ollama is running (`ollama serve` or the desktop app).

### 5. Set environment variables

```bash
export DATABASE_URL="postgres://rag:rag@localhost:5432/ragdb"
export DOCS_PATH="$HOME/formance-docs"
```

Add these to your shell profile (`~/.zshrc`, `~/.bashrc`) to avoid repeating them.

## First run

Run the three commands in order — only needed once (or after a docs update):

```bash
# 1. Create the pgvector extension and the doc_chunks table
go run . migrate

# 2. Parse, embed and index all documentation (~5–15 min depending on hardware)
go run . ingest

# 3. Start the web UI
go run . serve
```

Then open **http://localhost:8080**.

## Security

Two independent rate-limiting layers (defence in depth):

- **Go middleware** — 5 req/min per IP (burst 3) on `POST /api/ask` and `POST /api/feedback`; MCP tool calls get their own, separate budget (20/min, burst 5) so agent traffic and browser traffic never share a bucket. Both honour `X-Forwarded-For`/`X-Real-IP`, but only from a trusted proxy — see `TRUSTED_PROXIES` below. Stale per-IP entries are garbage-collected automatically. Exceeding the limit returns `429` with a friendly message in the UI (or a plain `429` JSON response for MCP).
- **nginx** (production) — same `/api/ask` limit enforced at the network edge before requests reach the app (see below).

Input hardening on `/api/ask`: request body capped at 256 KB, question at 2 000 characters, history at the last 12 turns, `top_k` at 30. The system prompt also instructs the model to treat the user question as data, not instructions (prompt-injection mitigation).

**MCP endpoint** (`/api/mcp`) — authentication is optional, controlled by `MCP_TOKEN`. When set, every request must carry `Authorization: Bearer <MCP_TOKEN>` (checked in constant time); missing or wrong tokens get `401` with a `WWW-Authenticate: Bearer` header, and the request never reaches the tool pipeline. When `MCP_TOKEN` is unset the endpoint stays open for backward compatibility, and the server logs a startup warning that it is unauthenticated. Either way, the endpoint is rate-limited (see above).

**Trusted proxies** — `X-Forwarded-For` and `X-Real-IP` are only honoured when the request's `RemoteAddr` is itself a trusted proxy (`TRUSTED_PROXIES`, default `127.0.0.1/32,::1/128` — i.e. nginx on the same host). Otherwise those headers are client-controlled and would let anyone spoof their IP to dodge or pollute the rate limiter. When trusted, `X-Forwarded-For` is walked right-to-left to skip any trusted-proxy hops and find the address the proxy chain actually observed.

## Feedback & analytics

- **👍/👎 buttons** under every answer — stored in the `feedback` table with the question and answer.
- **Request logging** — every `/api/ask` call is recorded (duration, chunks found, status: `ok` / `error` / `no_results` / `cancelled`, the last one meaning the client disconnected mid-request rather than the pipeline failing).
- **`GET /stats`** — monitoring dashboard in the browser: total & today's requests, average duration, error rate, feedback volume and positive rate. Also available as raw JSON at `GET /api/stats`.

Both tables are created with `IF NOT EXISTS` and survive `migrate` runs (only `doc_chunks` is dropped and rebuilt).

## Production deployment (nginx)

For a customer-facing deployment, put nginx in front of the Go server. It handles rate limiting at the network edge, before requests reach the app, and passes the real client IP via `X-Real-IP` / `X-Forwarded-For` so the Go-level rate limiter also works correctly — every `location` block in `nginx.conf` that sets its own `proxy_set_header` repeats these, since nginx does not merge them in from the `server{}` block once a `location{}` sets its own.

```bash
# Copy the provided config
sudo cp nginx.conf /etc/nginx/sites-available/docs-rag
sudo ln -s /etc/nginx/sites-available/docs-rag /etc/nginx/sites-enabled/docs-rag

# Test and reload
sudo nginx -t && sudo systemctl reload nginx
```

Key settings in `nginx.conf`:
- **Rate limit**: 5 req/min per IP, burst of 3 — applied only on `POST /api/ask`
- **SSE streaming**: `proxy_buffering off` + `proxy_http_version 1.1` on both `/api/ask` and `/api/mcp` (the MCP streamable HTTP transport keeps a long-lived GET stream open the same way) so tokens/messages stream through in real time
- **Timeout**: `proxy_read_timeout 120s` on `/api/ask` (LLM generation can take 60s+) and `600s` on `/api/mcp` (agent sessions can idle between tool calls) — don't cut either short

The Go server also enforces its own rate limits independently (defence in depth): 5 req/min for `/api/ask`/`/api/feedback`, 20 req/min for `/api/mcp`. Set your domain in the `server_name` directive.

| `ANSWER_EMBED_TIMEOUT` | no | `10s` | Per-request budget for the embed stage. |
| `ANSWER_SEARCH_TIMEOUT` | no | `5s` | Per-request budget for the retrieval stage. |
| `ANSWER_TOTAL_BUDGET` | no | `120s` | Overall budget for one `/api/ask` pipeline run — translate, embed, search and generation combined. |

## Health and shutdown

- **`GET /healthz`** — liveness probe. Always `200 ok`, no database call: a DB outage should surface as "not ready" (see below), not as a reason to restart an otherwise-healthy process.
- **`GET /readyz`** — readiness probe. Pings the database with a 2s timeout; `200 ok` when reachable, `503` otherwise. Point a load balancer or orchestrator at this one to stop routing traffic to an instance that can't complete a request.

Neither endpoint is rate-limited (a health check polling every few seconds must never share the `/api/ask` budget) or written to `request_logs` (they're infrastructure plumbing, not documentation questions, and would skew the `/stats` analytics).

**Graceful shutdown** — `serve` runs under a context cancelled on SIGINT/SIGTERM (`cmd.Execute`'s `signal.NotifyContext`). On shutdown it stops accepting new connections, then handles three kinds of in-flight work differently:

- **Open MCP GET streams** (the streamable HTTP transport's server-to-client channel) are cancelled **immediately**, not drained. They carry no in-progress answer to finish — the underlying `mcp-go-sdk` handler simply blocks on its request context until the client goes away — so leaving one open would hold up shutdown for the full `SHUTDOWN_TIMEOUT` for no benefit. `/api/ask` streams and MCP tool calls (`POST`) are untouched by this and keep draining normally.
- **`/api/ask` answers and MCP tool calls** drain normally for up to `SHUTDOWN_TIMEOUT` (default 20s) — they are already bounded by `ANSWER_TOTAL_BUDGET` per request, so most finish on their own well before that.
- If `SHUTDOWN_TIMEOUT` elapses with requests still running, everything left is **forcibly cancelled**: the context of every in-flight `/api/ask` request and MCP tool call is cancelled (unblocking any handler that respects `ctx`, which every pipeline stage does), the listener and its connections are force-closed, and after a short grace period (5s) for handlers and tool calls to actually unwind, `serve` proceeds regardless. MCP tool calls need their own cancel signal for this: the `mcp-go-sdk` runs them on a context that drops the HTTP server's cancellation. From the moment that grace period starts, new work is refused: a request that still arrives gets `503` with `Connection: close`, a tool call gets a `server shutting down` tool error.

The worst-case exit is therefore `SHUTDOWN_TIMEOUT` + 5s handler grace + 5s request-log drain (below) = 30s with the default, which fits the 30s `terminationGracePeriodSeconds` Kubernetes defaults to. If you raise `SHUTDOWN_TIMEOUT`, set your orchestrator's grace period to at least `SHUTDOWN_TIMEOUT` + 10s, or it will SIGKILL `serve` before the drain finishes. A **second** SIGINT/SIGTERM during shutdown kills the process immediately (default signal handling is restored after the first), for when you'd rather not wait.

Only **after** that — draining in-flight request-log writes, which each self-bound (`logWriteTimeout`, 5s) — does `serve` close the database pool, so a write that started just before shutdown never runs against an already-closed pool; any request-log write attempted after draining begins is rejected (logged, not silently dropped) rather than racing that drain.

`http.Server` has no `WriteTimeout`: it applies to a whole response including the body, and would sever a long-running SSE stream mid-token; `ReadHeaderTimeout` (10s) and `IdleTimeout` (120s) bound a slow or idle client without touching an active response.

**Outbound HTTP** — the embedder and LLM clients set a dial timeout (5s) and TLS handshake timeout (5s) on their transport, plus a response-header timeout (time to first byte: 30s for the embedder, 60s for the LLM by default, overridable via `LLM_RESPONSE_HEADER_TIMEOUT` — see the environment variables table above). Neither client sets an overall `http.Client.Timeout`: `EmbedBatch` can legitimately run long for a big ingest batch, and the LLM client's response is itself a long streamed answer — a blanket deadline would cut either off along with a genuinely hung connection. Per-request bounds come from `answer.go`'s stage timeouts above instead. Note that a cold local `qwen2.5:32b` (nothing resident in GPU/RAM yet) can take longer than both `ANSWER_TRANSLATE_TIMEOUT` (10s) and the LLM response-header timeout (60s) just to start responding — raise either, or keep the model warm with Ollama's `keep_alive` option, if cold-start latency is a recurring problem rather than a one-off.

## Stack

- **Go** — single binary, no runtime dependencies
- **Ollama** — `nomic-embed-text` (embeddings, task prefixes) + `qwen2.5:32b` (generation at temp 0.2 + translation)
- **PostgreSQL 17 + pgvector** — HNSW index for vector search, GIN index for BM25 full-text search; also stores feedback and request analytics
- **Hybrid retrieval** — 70% vector similarity + 30% BM25 keyword score, combined in a single SQL query
- **Vanilla JS** — embedded web UI, no build step, SSE streaming
- **nginx + GitHub Actions** — production edge (rate limit, SSE passthrough) and daily automated index updates
