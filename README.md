# docs-rag

> 🚧 **Status: proof of concept.** Runs fully locally on your machine — no server deployed yet, no production LLM API connected yet. Response time (30–60s) reflects the local model, not the final product: a hosted LLM API will replace it before any customer-facing launch.

A local RAG (Retrieval-Augmented Generation) engine for the [Formance](https://formance.com) documentation. Ask questions about the platform in natural language — answers are generated by a local LLM using only the official docs as context. No external API keys, no data leaving your machine.

docs-rag is also the producer of the Formance docs for the support bot's Amazon Bedrock Knowledge Base. The `publish-kb` command reuses the chunker and the metadata extraction, and the knowledge base does the embeddings and storage. It is separate from the local path above, which is unchanged. See [Publish to the Bedrock Knowledge Base](#publish-to-the-bedrock-knowledge-base).

---

## How it works

```
Question → translate EN → embed → hybrid search (vector + BM25) → diversity filter → top chunks → qwen2.5:32b → streamed answer
```

1. **Ingest** — the Formance docs repo is walked, `.md`/`.mdx` files are parsed, MDX/JSX noise is stripped, and the text is split into ~500-token chunks by heading hierarchy (H2 → H3). Each chunk is prefixed with a **full breadcrumb** (`Page Title > H2 > H3`) so the embedding model captures the page context.
2. **Embed** — each chunk is embedded via Ollama (`nomic-embed-text`, 768 dims) using the model's `search_document:` task prefix, and stored in PostgreSQL alongside a `tsvector` column (for full-text search) with a pgvector HNSW index and a GIN index.
3. **Translate** — at query time the question is translated to English (the language of the docs) before embedding, so French or other-language questions match correctly. The query is embedded with the `search_query:` prefix.
4. **Hybrid search** — retrieval combines **vector similarity** (70%) and **BM25 keyword matching** (30%) in a single SQL query. This means exact technical terms (`ErrMetadataOverride`, `fctl ledger send`, `unbounded`) are found reliably even when semantic similarity alone would miss them.
5. **Diversity filter** — the candidate pool (top-k×2) is deduplicated so no single source file contributes more than 2 chunks to the final context.
6. **Generate** — the retrieved chunks are injected into the system prompt of `qwen2.5:32b` via Ollama (temperature 0.2 for factual answers). The model answers strictly from the docs for technical facts, and may synthesise step-by-step guidance from documented concepts. Active filters (version, deployment, license) are also injected so the LLM knows what scope it is operating in. In Community mode, the list of Enterprise-only features is **derived live from the badges in the database** (cached 5 min), so the guard stays in sync with the docs; the model must flag EE features as such, and may offer a clearly-labeled Community alternative when one exists.
7. **Stream** — the answer is streamed token by token to the web UI via SSE. Each answer gets 👍/👎 feedback buttons, stored for quality monitoring.

## Setup

### 1. Clone this repo

```bash
git clone https://github.com/celestingeniaut/docs-rag
cd docs-rag
```

### 2. Clone the Formance docs

```bash
git clone https://github.com/formancehq/docs ~/formance-docs
```

You can put it anywhere — you will point `DOCS_PATH` at it.

### 3. Start PostgreSQL

```bash
docker compose up -d
```

This starts a `pgvector/pgvector:pg17` container on port 5432 with credentials `rag / rag / ragdb`.

### 4. Pull the Ollama models

```bash
# Embedding model (fast, ~270 MB)
ollama pull nomic-embed-text

# Generation + translation model (slow to pull, ~20 GB — grab a coffee)
ollama pull qwen2.5:32b
```

Make sure Ollama is running (`ollama serve` or the desktop app).

### 5. Set environment variables

```bash
export DATABASE_URL="postgres://rag:rag@localhost:5432/ragdb"
export DOCS_PATH="$HOME/formance-docs"
```

Add these to your shell profile (`~/.zshrc`, `~/.bashrc`) to avoid repeating them.

## Security

Two independent rate-limiting layers (defence in depth):

- **Go middleware** — 5 req/min per IP (burst 3) on `POST /api/ask` and `POST /api/feedback`; MCP tool calls get their own, separate budget (20/min, burst 5) so agent traffic and browser traffic never share a bucket. Both honour `X-Forwarded-For`/`X-Real-IP`, but only from a trusted proxy — see `TRUSTED_PROXIES` below. Stale per-IP entries are garbage-collected automatically. Exceeding the limit returns `429` with a friendly message in the UI (or a plain `429` JSON response for MCP).
- **nginx** (production) — same `/api/ask` limit enforced at the network edge before requests reach the app (see below).

Input hardening on `/api/ask`: request body capped at 256 KB, question at 2 000 characters, history at the last 12 turns, `top_k` at 30. The system prompt also instructs the model to treat the user question as data, not instructions (prompt-injection mitigation).

**MCP endpoint** (`/api/mcp`) — authentication is optional, controlled by `MCP_TOKEN`. When set, every request must carry `Authorization: Bearer <MCP_TOKEN>` (checked in constant time); missing or wrong tokens get `401` with a `WWW-Authenticate: Bearer` header, and the request never reaches the tool pipeline. When `MCP_TOKEN` is unset the endpoint stays open for backward compatibility, and the server logs a startup warning that it is unauthenticated. Either way, the endpoint is rate-limited (see above).

**Trusted proxies** — `X-Forwarded-For` and `X-Real-IP` are only honoured when the request's `RemoteAddr` is itself a trusted proxy (`TRUSTED_PROXIES`, default `127.0.0.1/32,::1/128` — i.e. nginx on the same host). Otherwise those headers are client-controlled and would let anyone spoof their IP to dodge or pollute the rate limiter. When trusted, `X-Forwarded-For` is walked right-to-left to skip any trusted-proxy hops and find the address the proxy chain actually observed.

## Feedback & analytics

- **👍/👎 buttons** under every answer — stored in the `feedback` table with the question and answer.
- **Request logging** — every `/api/ask` call is recorded (duration, chunks found, status: `ok` / `error` / `no_results` / `cancelled`, the last one meaning the client disconnected mid-request rather than the pipeline failing).
- **`GET /stats`** — monitoring dashboard in the browser: total & today's requests, average duration, error rate, feedback volume and positive rate. Also available as raw JSON at `GET /api/stats`.

Both tables are created with `IF NOT EXISTS` and survive `migrate` runs (only `doc_chunks` is dropped and rebuilt).

## Review page

An internal page where teammates grade the support bot's draft answers (the bot lives in `formancehq/support-agent`). One card at a time: the customer question, the bot's answer (rendered markdown, links open in a new tab), and the team's real reply folded away for comparison. Grades are **Wrong** (`bad`), **Needs work** (`meh`: useful but needs editing) or **Good** (`good`), with an optional note. Swipe on a phone or trackpad, use the arrow keys (left, up, right), or tap the buttons. Shift+wheel is ignored: it is horizontal mouse scrolling, not a trackpad swipe.

There is no login: the service is only reachable over Tailscale, and the page asks nobody for a name. Each browser keeps a random reviewer id in `localStorage` (in memory if storage is blocked). Clearing browser data makes you a new reviewer.

| Route | Auth | Purpose |
|-------|------|---------|
| `GET /review` | none | The grading page. Served with a strict Content-Security-Policy (no inline script or style, no images, same-origin only); JS and CSS come from `/review/app.js` and `/review/app.css`. |
| `GET /api/review/next?reviewer=<id>` | none | Next item this reviewer has not graded. Items with the fewest grades come first. |
| `POST /api/review/grades` | none | Grade an item (upsert). |
| `DELETE /api/review/grades` | none | Undo: delete the caller's own grade. |
| `POST /api/review/batches` | `x-review-token` | Import a batch of drafts. |
| `GET /api/review/results?batch_id=<id>` | `x-review-token` | List every grade of a batch. |

The two admin routes compare the `x-review-token` header with `REVIEW_ADMIN_TOKEN` in constant time. **There is no default**: when `REVIEW_ADMIN_TOKEN` is unset both routes answer `503`; a missing or wrong token gets `401`. The three grading routes are open and validate every field instead. All write routes share one per-IP rate limiter (120 req/min, burst 30), separate from `/api/ask`.

**Import.** `POST /api/review/batches` with `{"batch_id": "...", "items": [{"item_id", "ticket_key", "question", "draft", "team_reply", "decision", "score"}]}`. `item_id`, `question` and `draft` are required (so is `batch_id`); `ticket_key`, `team_reply`, `decision` and `score` are optional. Limits: body 8 MiB (`413`), 500 items, `item_id`/`batch_id` 200 bytes, `question` 20 000, `draft` and `team_reply` 100 000, `ticket_key` 100, `decision` 100; no NUL bytes. The whole request is validated first (`400` names the bad item), then inserted in one transaction. The response is `{"batch_id", "received", "inserted", "skipped"}`.

Import is **idempotent on `item_id` and never updates**: an `item_id` that already exists is skipped (`ON CONFLICT DO NOTHING`), even if the new draft differs or the item came under another `batch_id`. That keeps every grade attached to the exact text that was graded. To re-grade a changed draft, send it under a new `item_id`.

**Grading.** `GET /api/review/next` answers `{"done": false, "item": {"item_id", "ticket_key", "question", "draft_html", "team_reply"}, "progress": {"graded", "total"}}`, or `{"done": true, "item": null, "progress": {...}}` when nothing is left. `question` and `team_reply` are plain text (the page inserts them with `textContent`); `draft_html` is the draft rendered server-side with goldmark. Raw HTML is dropped, only `http`, `https` and `mailto` links survive (others become `#`), images become plain links, and every link gets `target="_blank" rel="noopener noreferrer"`. The `decision` and `score` from the import are not sent to reviewers, so they cannot bias the grade.

`POST /api/review/grades` takes `{"item_id", "reviewer", "grade", "note"}` and answers `204`. `reviewer` is 8-64 characters of `A-Za-z0-9_-`, `grade` is `bad`, `meh` or `good`, `note` is at most 2 000 characters, the body at most 16 KiB; an unknown item is `404`. Grading an item again replaces the earlier grade and note (one row per item and reviewer).

**Undo.** `DELETE /api/review/grades` takes `{"item_id", "reviewer"}` and removes only that reviewer's own grade. It answers `200` with that item in the same shape as `/api/review/next` (so the page shows it again), or `404` when that reviewer had no grade on it.

**Results.** `GET /api/review/results?batch_id=b1` answers `{"batch_id": "b1", "grades": [{"item_id", "reviewer_id", "grade", "note", "created_at"}]}`, ordered by item. `created_at` is the time of the latest grade (a regrade updates it).

```bash
# Import a batch (same call twice: the second reports "inserted": 0)
curl -sS -X POST https://rag.example.com/api/review/batches \
  -H "x-review-token: $REVIEW_ADMIN_TOKEN" -H "Content-Type: application/json" \
  -d '{"batch_id":"2026-11-12","items":[{"item_id":"SUP-123-a","ticket_key":"SUP-123","question":"How do I ...?","draft":"Use **numscript** ... [docs](https://docs.formance.com)","team_reply":"...","decision":"send","score":0.82}]}'
# {"batch_id":"2026-11-12","received":1,"inserted":1,"skipped":0}

# Fetch the grades
curl -sS -H "x-review-token: $REVIEW_ADMIN_TOKEN" \
  "https://rag.example.com/api/review/results?batch_id=2026-11-12"
```

**Deploying.** Set `REVIEW_ADMIN_TOKEN` in the server's environment (a long random string; without it the import and results routes stay disabled), and run `rag migrate` to create `review_items` and `review_grades` (idempotent, safe to re-run; existing tables are untouched). With nginx, `/review` and `/api/review/*` already fall under `location /`; `nginx.conf` adds one block for `POST /api/review/batches` that raises `client_max_body_size` to 9m (nginx's 1m default would reject large batches). Share the `/review` URL with teammates on the Tailscale network.

## Production deployment (nginx)

For a customer-facing deployment, put nginx in front of the Go server. It handles rate limiting at the network edge, before requests reach the app, and passes the real client IP via `X-Real-IP` / `X-Forwarded-For` so the Go-level rate limiter also works correctly — every `location` block in `nginx.conf` that sets its own `proxy_set_header` repeats these, since nginx does not merge them in from the `server{}` block once a `location{}` sets its own.

```bash
# Copy the provided config
sudo cp nginx.conf /etc/nginx/sites-available/docs-rag
sudo ln -s /etc/nginx/sites-available/docs-rag /etc/nginx/sites-enabled/docs-rag

# Test and reload
sudo nginx -t && sudo systemctl reload nginx
```

Key settings in `nginx.conf`:
- **Rate limit**: 5 req/min per IP, burst of 3 — applied only on `POST /api/ask`
- **SSE streaming**: `proxy_buffering off` + `proxy_http_version 1.1` on both `/api/ask` and `/api/mcp` (the MCP streamable HTTP transport keeps a long-lived GET stream open the same way) so tokens/messages stream through in real time
- **Timeout**: `proxy_read_timeout 120s` on `/api/ask` (LLM generation can take 60s+) and `600s` on `/api/mcp` (agent sessions can idle between tool calls) — don't cut either short

The Go server also enforces its own rate limits independently (defence in depth): 5 req/min for `/api/ask`/`/api/feedback`, 20 req/min for `/api/mcp`. Set your domain in the `server_name` directive.

## Publish to the Bedrock Knowledge Base

`publish-kb` publishes the Formance docs to the support bot's Amazon Bedrock Knowledge Base (S3 Vectors, `eu-west-1`). The existing Ollama and pgvector path (`ingest`, `serve`, `/api/ask`, MCP, web UI) is unchanged and still works. `publish-kb` needs neither PostgreSQL nor Ollama.

It reuses the chunker and the metadata extraction. The knowledge base computes the embeddings and stores the vectors. The command:

1. Builds one markdown file per chunk under `docs/`, each with a `<name>.md.metadata.json` sidecar. A chunk over about 1500 bytes or 400 estimated tokens is re-split, with the breadcrumb repeated in each part. Re-splits use paragraph or line boundaries. A code block over the budget is split at line boundaries, and each part closes and reopens its code fence. A file usually stays under 512 tokens. The token estimate is conservative: text inside code fences and lines with more than 12% symbol characters count 2 characters per token, prose 4, and each non-ASCII character 1 token (`internal/kbpublish/tokens.go`). The dry run reports the chunks re-split for tokens and the largest estimate. A chunk whose version range no Stack release ships is excluded and listed in the dry-run. The metadata mapping is in [docs/kb-contract-changes.md](docs/kb-contract-changes.md).
2. Validates every key, every sidecar and the token budget of every file. A file over 400 estimated tokens is refused.
3. Diffs the files against `s3://<bucket>/docs/`. Each object carries the `x-amz-meta-sha256` of its body plus sidecar, and a file whose hash matches is left alone.
4. Uploads the new and changed files, then deletes the stale objects.
5. Starts one ingestion job, waits for it, and prints its statistics and failure reasons.

### Build

The Bedrock Agent adapter (`internal/kbpublish/aws_bedrock.go`) builds by default. Its dependency, `github.com/aws/aws-sdk-go-v2/service/bedrockagent` v1.69.2, is pinned in `go.mod`.

```bash
go build -o rag .
```

### Usage

Dry run is the default. Credentials come from the standard AWS chain (for example `AWS_PROFILE`). Nothing is read from the repository, and no secret belongs in it.

```bash
export DOCS_PATH="$HOME/formance-docs"

# Offline dry run: no AWS call, diffs against an empty bucket, writes the files to ./kb-out
./rag publish-kb --offline --out ./kb-out

# Online dry run: diffs against the bucket, writes nothing
export AWS_PROFILE=formance-internal-bedrock
export SOURCE_BUCKET=<source-bucket>
./rag publish-kb

# Real publish
export KB_ID=<knowledge-base-id> DS_ID=<data-source-id>
./rag publish-kb --dry-run=false
```

`--offline` cannot publish: it makes no AWS call.

A flag wins over its environment variable.

| Flag | Environment variable | Default | Description |

| `--out` | — | — | Also write the generated files and sidecars under this directory. |

| `--kb-id` | `KB_ID` | — | Knowledge base id. Required to publish. |
| `--data-source-id` | `DS_ID` | — | Data source id. Required to publish. |
| `--region` | `AWS_REGION` | `eu-west-1` | AWS region. Only `eu-*` regions are accepted. |
| `--allow-mass-delete` | — | `false` | Allow deleting more than 20% of the existing objects. |

### Safety

- The command deletes only under `docs/`. It refuses any delete key outside that prefix.
- It refuses a run that would delete more than 20% of the existing objects, which usually means a wrong `DOCS_PATH` or a broken parse. Pass `--allow-mass-delete` to override. The guard also applies to the online dry run.
- Validation stops the run before any AWS call. A file that fails to parse, a validation error, or an empty result produces an error and nothing is published.
- Uploads write the sidecar first, so a body never exists without its metadata.
- When nothing changed, the command still starts a sync, so a crashed earlier run is resumed. It skips the sync only when the latest docs-rag ingestion job meets all three conditions:
  - It is `COMPLETE` with 0 failed documents.
  - It started after the newest object under `docs/` was modified.
  - Its description carries the current plan hash (`docs-rag plan=<sha256>`, computed from the sorted list of keys and hashes). The hash also catches a crash after a delete-only run, because deleted objects leave no modification date.

  The command waits for a running job, then checks again. `--force-sync` always starts one.
- An ingestion error suggests re-running with `--force-sync`.
- Exit codes: `0` on success, `1` on any error (including validation, the delete guards, and a failed ingestion job).

### Verify after a publish

`scripts/kb-verify.sh` runs read-only `Retrieve` calls against the knowledge base. It tests the numeric version filters first, then the deployment and license filters, then the bot's combined filter. It requires the `aws` CLI v2 and `jq`.

```bash
AWS_PROFILE=formance-internal-bedrock scripts/kb-verify.sh --kb-id <knowledge-base-id> [--stack-version 3.1] [--results 10] [--region eu-west-1] [--preflight]
```

`--preflight` also checks that the knowledge base exists. Run `scripts/kb-verify.sh --help` for the query options. Exit codes: `0` when no test fails, `1` on any failure, `2` on a configuration error.

Run the offline tests of the script with:

```bash
bash tests/kb-verify/run.sh
```

CI (`.github/workflows/test.yml`) has a build job and runs these offline tests.

### Before automating publish-kb

Manual runs are safe as they are. These items are required before `publish-kb` runs unattended (CI, cron):

- [ ] **Per-bucket lock.** `publish-kb` has no lock today, so two publishers can interleave uploads and deletes. Take a lock object in the source bucket with an S3 conditional write (`If-None-Match: *`) for the whole run, through ingestion. Run automated publishes in a single CI concurrency group.
- [ ] **Unsynced-changes marker.** Write a marker before any S3 change, and clear it only after a successful ingestion job. A crash after deletes then always triggers a sync on the next run. Today's plan-hash check misses a delete-only crash that returns to an older plan when another writer has touched `docs/`.
- [ ] **Failure-injection tests.** Cover a failure between the sidecar and body writes, and a failure midway through deletions. Rerun each, then assert the stored bytes and that ingestion runs.
- [ ] **Retry test for `ConflictException`.** Add a dedicated test that `Syncer.Run` retries on `ConflictException` (another ingestion job running) until `--timeout`, for both changed and `--force-sync` runs.

| `ANSWER_EMBED_TIMEOUT` | no | `10s` | Per-request budget for the embed stage. |
| `ANSWER_SEARCH_TIMEOUT` | no | `5s` | Per-request budget for the retrieval stage. |
| `ANSWER_TOTAL_BUDGET` | no | `120s` | Overall budget for one `/api/ask` pipeline run — translate, embed, search and generation combined. |
| `LLM_RESPONSE_HEADER_TIMEOUT` | no | `60s` | Time-to-first-byte bound on the LLM transport (see "Outbound HTTP" below). A cold local model — nothing yet resident in GPU/RAM, still loading a ~20GB file — can take longer than 60s to emit its first token; raise this (and `ANSWER_TRANSLATE_TIMEOUT`, which a cold model can also exceed) or keep the model warm (Ollama's `keep_alive`) instead of hitting this on every first request after idle. Same zero/negative-rejected rule as the timeouts above. |

The `publish-kb` variables (`SOURCE_BUCKET`, `KB_ID`, `DS_ID`, `AWS_REGION`) are listed in [Publish to the Bedrock Knowledge Base](#flags-and-environment-variables). `DOCS_PATH` is shared.

> **Generation is OpenAI-compatible.** The same client talks to local Ollama (`/v1/chat/completions`) or a hosted LiteLLM gateway — switching provider/model is pure config (`LLM_BASE_URL` + `LLM_API_KEY` + `LLM_MODEL`), no code change. Embeddings stay on Ollama's `nomic-embed-text` regardless.

## Health and shutdown

- **`GET /healthz`** — liveness probe. Always `200 ok`, no database call: a DB outage should surface as "not ready" (see below), not as a reason to restart an otherwise-healthy process.
- **`GET /readyz`** — readiness probe. Pings the database with a 2s timeout; `200 ok` when reachable, `503` otherwise. Point a load balancer or orchestrator at this one to stop routing traffic to an instance that can't complete a request.

Neither endpoint is rate-limited (a health check polling every few seconds must never share the `/api/ask` budget) or written to `request_logs` (they're infrastructure plumbing, not documentation questions, and would skew the `/stats` analytics).

**Graceful shutdown** — `serve` runs under a context cancelled on SIGINT/SIGTERM (`cmd.Execute`'s `signal.NotifyContext`). On shutdown it stops accepting new connections, then handles three kinds of in-flight work differently:

- **Open MCP GET streams** (the streamable HTTP transport's server-to-client channel) are cancelled **immediately**, not drained. They carry no in-progress answer to finish — the underlying `mcp-go-sdk` handler simply blocks on its request context until the client goes away — so leaving one open would hold up shutdown for the full `SHUTDOWN_TIMEOUT` for no benefit. `/api/ask` streams and MCP tool calls (`POST`) are untouched by this and keep draining normally.
- **`/api/ask` answers and MCP tool calls** drain normally for up to `SHUTDOWN_TIMEOUT` (default 20s) — they are already bounded by `ANSWER_TOTAL_BUDGET` per request, so most finish on their own well before that.
- If `SHUTDOWN_TIMEOUT` elapses with requests still running, everything left is **forcibly cancelled**: the context of every in-flight `/api/ask` request and MCP tool call is cancelled (unblocking any handler that respects `ctx`, which every pipeline stage does), the listener and its connections are force-closed, and after a short grace period (5s) for handlers and tool calls to actually unwind, `serve` proceeds regardless. MCP tool calls need their own cancel signal for this: the `mcp-go-sdk` runs them on a context that drops the HTTP server's cancellation. From the moment that grace period starts, new work is refused: a request that still arrives gets `503` with `Connection: close`, a tool call gets a `server shutting down` tool error.

The worst-case exit is therefore `SHUTDOWN_TIMEOUT` + 5s handler grace + 5s request-log drain (below) = 30s with the default, which fits the 30s `terminationGracePeriodSeconds` Kubernetes defaults to. If you raise `SHUTDOWN_TIMEOUT`, set your orchestrator's grace period to at least `SHUTDOWN_TIMEOUT` + 10s, or it will SIGKILL `serve` before the drain finishes. A **second** SIGINT/SIGTERM during shutdown kills the process immediately (default signal handling is restored after the first), for when you'd rather not wait.

Only **after** that — draining in-flight request-log writes, which each self-bound (`logWriteTimeout`, 5s) — does `serve` close the database pool, so a write that started just before shutdown never runs against an already-closed pool; any request-log write attempted after draining begins is rejected (logged, not silently dropped) rather than racing that drain.

`http.Server` has no `WriteTimeout`: it applies to a whole response including the body, and would sever a long-running SSE stream mid-token; `ReadHeaderTimeout` (10s) and `IdleTimeout` (120s) bound a slow or idle client without touching an active response.

**Outbound HTTP** — the embedder and LLM clients set a dial timeout (5s) and TLS handshake timeout (5s) on their transport, plus a response-header timeout (time to first byte: 2 min for the embedder — Ollama answers only once a whole batch is embedded, and a full-window chunk alone takes ~24s on a CPU — and 60s for the LLM by default, overridable via `LLM_RESPONSE_HEADER_TIMEOUT` — see the environment variables table above). Neither client sets an overall `http.Client.Timeout`: `EmbedBatch` can legitimately run long for a big ingest batch, and the LLM client's response is itself a long streamed answer — a blanket deadline would cut either off along with a genuinely hung connection. Per-request bounds come from `answer.go`'s stage timeouts above instead. Note that a cold local `qwen2.5:32b` (nothing resident in GPU/RAM yet) can take longer than both `ANSWER_TRANSLATE_TIMEOUT` (10s) and the LLM response-header timeout (60s) just to start responding — raise either, or keep the model warm with Ollama's `keep_alive` option, if cold-start latency is a recurring problem rather than a one-off.

## Stack

- **Go** — single binary, no runtime dependencies
- **Ollama** — `nomic-embed-text` (embeddings, task prefixes) + `qwen2.5:32b` (generation at temp 0.2 + translation)
- **PostgreSQL 17 + pgvector** — HNSW index for vector search, GIN index for BM25 full-text search; also stores feedback and request analytics
- **Hybrid retrieval** — 70% vector similarity + 30% BM25 keyword score, combined in a single SQL query
- **Vanilla JS** — embedded web UI, no build step, SSE streaming
- **nginx + GitHub Actions** — production edge (rate limit, SSE passthrough) and daily automated index updates
- **Amazon Bedrock Knowledge Base** — target of `publish-kb` (S3 Vectors, `eu-west-1`), which does its own embeddings
